# E17-S06: `PositionAPI.close()` Direction-Blind Cash Update

**Epic:** E17 — CFD Margin & Order-Fill Correctness
**Phase:** Bug (found during downstream validation, not part of a feature sequence)

## Description

The standalone manual-close endpoint, `PositionAPI.close()`, updates account
cash with a formula that doesn't check the position's `direction` or
`instrument_type`:

```python
account_updated = account_before.model_copy(
    update={"cash": account_before.cash + exit_price * quantity - costs.total}
)
```

This is correct only for a long stock position (full notional in, full
notional back out). It's wrong for:

- **Any short position** — a winning short (price fell) should return MORE
  cash than this formula gives it; `exit_price * quantity` alone doesn't
  reflect that P&L is `entry - exit` for a short, not `exit` in isolation.
- **Any CFD position** (which covers every short, plus futures/forex/crypto
  by ticker convention) — only `margin_required` was posted at entry, not
  full notional, so the cash returned at close should be `margin_required +
  realized_pnl + entry_costs`, not `exit_price * quantity`.

`SimulationEngine._close_cash_return()` (src/phantom/engine/simulation_engine.py,
fixed as part of `ee31835`) already implements the correct, direction-aware,
instrument-type-aware formula for the `run_backtest()`/`run_paper()` internal
close path:

```python
@staticmethod
def _close_cash_return(position, closed, exit_costs) -> float:
    if position.instrument_type == "cfd":
        entry_costs = position.commission_entry + position.spread_cost + position.slippage_cost
        return position.margin_required + (closed.realized_pnl or 0.0) + entry_costs
    return closed.exit_price * position.quantity - exit_costs.total
```

`PositionAPI.close()` never adopted this fix — it's a separate code path
(calls `PositionManager.close()` for the position-row update, then does its
OWN, older cash update inline) that was apparently missed when
`_close_cash_return()` was introduced.

This was caught because a downstream project (Kairos) explicitly avoids
calling `ph.positions.close()` anywhere in its own code specifically because
of this bug — its `_liquidate_position()` force-closes positions via direct
SQL instead, with a comment citing "phantom's cash/short-PnL handling is
wrong for shorts." That avoidance can be removed once this is fixed.

## File Locations

- `src/phantom/api/positions.py` — `PositionAPI.close()` (~line 50-100+), the
  full-close cash update (~line 91-96)
- `src/phantom/engine/simulation_engine.py` — `_close_cash_return()`
  (reference implementation to reuse/mirror)

## Current State

See code excerpt above. Note `PositionAPI.close()` also supports a *partial*
close (`quantity < position.quantity`) — check whether `_close_cash_return()`
(built for full closes inside the day-loop) needs adaptation for that case,
or whether partial closes need their own proportional variant.

## Acceptance Criteria

- [ ] `PositionAPI.close()`'s cash update matches
      `SimulationEngine._close_cash_return()`'s logic for CFD positions
      (`margin_required + realized_pnl + entry_costs`, direction already
      correct via `realized_pnl`) and for stock positions (full notional in
      minus exit costs)
- [ ] A short CFD position closed via `ph.positions.close()` returns the same
      cash as an equivalent position closed via `runner.backtest()`'s
      TP/SL/max-time path, for identical entry/exit prices
- [ ] Partial closes remain correct (proportional margin/notional release)
- [ ] New test: open a short CFD position, close it profitably via
      `ph.positions.close()`, assert `account.cash` increases by the correct
      amount (not the old, direction-blind formula's wrong amount)
- [ ] New test: same scenario via `ph.orders.fill_manual()` +
      `ph.positions.close()` for a long stock position — confirm unchanged
      (already-correct) behavior

## Implementation Notes

Consider extracting `_close_cash_return()` out of `SimulationEngine` into a
shared location (e.g. `PositionManager` itself, alongside `close()`) so both
`PositionAPI.close()` and `SimulationEngine`'s three fill loops call the same
function — this is exactly the kind of duplicated-then-diverged logic that
already happened once with margin-rate lookups (E17-S01/E17-S03).
