# E17-S08: Bundled Margin Classes Only Match One Ticker Notation

**Epic:** E17 — CFD Margin & Order-Fill Correctness
**Phase:** Enhancement (found during downstream validation, not part of a feature sequence)

## Description

E17-S01 added per-instrument-class CFD margin rates (`MarginModel.classes`/
`margin_pct_for()`), but the bundled profiles (`ibkr.json`, `degiro.json`,
`xtb.json` — all three ship identical `classes`) only recognize ONE ticker
notation convention: broker-house-native symbol spellings (`"EURUSD"`,
`"XAUUSD"`, `"GOLD"`, `"OIL"`, and a `crypto` regex expecting bare
`"BTC"`/`"ETH"`/etc., optionally suffixed `USD`/`EUR` with no separator).

Any caller whose tickers come from a different, equally common convention —
e.g. Yahoo Finance's suffix style (`"EURUSD=X"`, `"GC=F"`, `"BTC-USD"`,
`"^GSPC"`), which a downstream project (Kairos) uses because it sources
market data from `price_cache`/yfinance — gets **zero** matches against any
bundled class: `symbols` is an exact-string list (no fuzzy/suffix matching),
and `match` is checked via `re.fullmatch`, so a ticker with an unexpected
suffix or separator never fullmatches a pattern built for the house
convention. Every such caller's `margin_pct_for()` call silently falls
through to `default_margin_pct` for 100% of its orders, regardless of asset
class, making E17-S01 dead code for it in practice — discovered exactly this
way when Kairos found its own leveraged FX/crypto tickers were all landing on
`default_margin_pct=0.25` (IBKR) despite `classes` existing.

Kairos worked around this by overwriting the loaded profile's `classes`
entirely with its own margin config, translated for `re.fullmatch`
compatibility (see E17-S07, filed alongside this ticket, for the API gap
that forced a raw SQL patch to do it) — but that's a per-caller fix. Any
other caller using a common alternate ticker convention hits the exact same
silent-fallthrough trap with no signal that anything is wrong (no error, no
warning — `margin_pct_for()` just returns a value, an unexpectedly flat one).

## File Locations

- `src/phantom/profiles/ibkr.json`, `degiro.json`, `xtb.json` — `margin.classes`
- `src/phantom/models/broker.py` — `MarginClassRule`/`MarginModel.margin_pct_for()`

## Current State

Example (`ibkr.json`, identical in the other two):

```json
{
  "label": "fx_majors",
  "match": "^[A-Z]{3}(USD|EUR|GBP|JPY|CHF|AUD|CAD|NZD)$",
  "margin_pct": 0.03
},
{
  "label": "index_commodity",
  "symbols": ["SPX500", "US30", "NAS100", "UK100", "GER40", "XAUUSD", "GOLD"],
  "margin_pct": 0.05
},
{
  "label": "other_commodity",
  "symbols": ["OIL", "WTI", "BRENT", "XAGUSD", "SILVER"],
  "margin_pct": 0.1
},
{
  "label": "crypto",
  "match": "^(BTC|ETH|XRP|LTC|BCH)(USD|EUR)?$",
  "margin_pct": 1.0
}
```

`re.fullmatch("^[A-Z]{3}(USD|EUR|GBP|JPY|CHF|AUD|CAD|NZD)$", "EURUSD=X")` is
`None`. `"GC=F" in ["SPX500", ..., "GOLD"]` is `False`. Neither the `symbols`
schema nor the `match` schema needs to change to fix this — both already
support arbitrary strings/regexes; the bundled *content* just only covers one
convention.

## Acceptance Criteria

- [ ] Each bundled class also recognizes the equivalent Yahoo Finance/yfinance
      ticker convention (the most common free data source, and the one that
      surfaced this): FX pairs suffixed `=X` (`"EURUSD=X"`), futures/commodities
      suffixed `=F` (`"GC=F"`, `"CL=F"`), major indices prefixed `^`
      (`"^GSPC"`, `"^DJI"`, `"^IXIC"`, `"^FTSE"`, `"^GDAXI"`), and crypto
      suffixed `-USD`/`-EUR` (`"BTC-USD"`, `"ETH-EUR"`) — either by adding
      alternate entries to each class's `symbols` list, or broadening `match`
      regexes to also accept the suffix/prefix form (e.g. via alternation)
- [ ] `margin_pct_for()` itself is unchanged — this is bundled-data-only, no
      schema or matching-logic change needed (confirmed above)
- [ ] Existing IBKR-native-symbol matches are unaffected (additive only)
- [ ] New test per bundled profile: `margin_pct_for("EURUSD=X")`,
      `margin_pct_for("GC=F")`, `margin_pct_for("BTC-USD")`,
      `margin_pct_for("^GSPC")` each resolve to their class's rate, not
      `default_margin_pct`
- [ ] `docs/library.md`'s `MarginModel`/`classes` section notes which ticker
      conventions the bundled profiles cover, so the next caller with a
      third convention knows to check rather than assume

## Implementation Notes

Not exhaustive — this only closes the gap for the specific conventions that
already caused a real, confirmed problem (yfinance-style). A caller using a
convention not covered here still needs E17-S07's update API to add its own.
Consider whether a short "supported ticker conventions" note belongs in each
bundled profile's own comments/docs, so this doesn't silently regress if a
class is added later without the yfinance-equivalent alongside it.
