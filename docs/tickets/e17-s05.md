# E17-S05: `fx_conversion_cost` Omitted From `realized_pnl`

**Epic:** E17 — CFD Margin & Order-Fill Correctness
**Phase:** Bug (found during downstream validation, not part of a feature sequence)

## Description

`PositionManager.close()` computes `realized_pnl` from gross P&L minus a cost
total that omits one of the four cost fields it charges at entry. `fx_conversion_cost`
is deducted from `account.cash` at fill time (via `OrderManager.handle_fill()`'s
`costs.total`, which includes fx) but is never subtracted back out of
`realized_pnl` at close time — so for any account whose `base_currency` differs
from the traded instrument's currency, every closed trade's `realized_pnl` is
overstated by exactly that trade's `fx_conversion_cost`.

This was caught because a downstream project (Kairos) has been running a
client-side correction for this exact gap since 2026-07-26/27 (predates all of
E17's other fixes) — `compute_corrected_realized_pnl()` in its
`kairos_papertrade.py`, root-caused in its own `docs/papertrade_loss_analysis.md`.
That correction is simple and already proven out in production use: `realized_pnl
- fx_conversion_cost`.

## File Locations

- `src/phantom/engine/position_manager.py` — `PositionManager.close()`
  (~line 333-368), the `all_costs` sum
- `src/phantom/costs/engine.py` — `CostEngine.exit_costs()`/`entry_costs()`,
  confirm `costs.fx` is the right field name for the closing-side fx cost (entry
  side already flows through `position.fx_conversion_cost`)

## Current State

```python
all_costs = (
    position.commission_entry
    + costs.commission
    + position.spread_cost
    + costs.spread
    + position.slippage_cost
    + costs.slippage
)
realized_pnl = gross_pnl - all_costs
```

No `fx_conversion_cost`/`costs.fx` term anywhere in this sum, despite
`position.fx_conversion_cost` existing as a stored field (set at fill time) and
being real money that left the account.

## Acceptance Criteria

- [ ] `all_costs` in `PositionManager.close()` includes
      `position.fx_conversion_cost` (entry-side fx cost, already stored on the
      position) — and any exit-side fx cost the closing trade itself incurs, if
      `CostEngine.exit_costs()` computes one
- [ ] `realized_pnl` for a closed position with a non-zero `fx_conversion_cost`
      matches the account's actual net cash change for that round trip (no
      residual gap)
- [ ] Existing tests for `realized_pnl` on fx-neutral (zero fx cost) positions
      are unaffected
- [ ] New test: open and close a position with a non-zero
      `fx_conversion_cost` (e.g. `base_currency != "USD"`), assert
      `realized_pnl` accounts for it and matches account cash delta exactly

## Implementation Notes

Kairos's `compute_corrected_realized_pnl()` (its `kairos_papertrade.py`) is a
working reference for the correct formula — it's a pure `realized_pnl -
fx_conversion_cost` subtraction, no other fields involved. This ticket is
"upstream" that fix so downstream callers can stop applying it client-side.
