# E17-S04: TP/SL and Margin-Call/Stop-Out Only Ever See One Bar's Resolution

**Epic:** E17 — CFD Margin & Order-Fill Correctness
**Phase:** Bug/enhancement (found during downstream validation, not part of a feature sequence)

## Description

`PositionManager.determine_close()` (TP/SL/trailing-stop/max-time) and
`MarginEngine.check()`/`handle_stop_out()` (margin-call/stop-out) both
evaluate exclusively against whatever single bar `SimulationEngine` hands
them for the current step — that bar's `High`/`Low`/`Close`, nothing finer:

```python
# position_manager.py, determine_close()
high = float(bar["High"])
low = float(bar["Low"])
close = float(bar["Close"])
```

That bar's own resolution is entirely up to whatever the caller's
`DataProvider.get_bars()` happens to return for the requested `start`/`end`
range — `SimulationEngine` has no concept of "the finest interval this
provider can supply" and never asks for one. If a caller runs a backtest at
daily resolution (a very normal thing to do — hourly/minute-level history is
often unavailable that far back, or would be prohibitively slow/large to
process day-by-day over a multi-year window), every TP/SL/liquidation
decision for that entire day collapses to "did the day's High/Low bracket
the trigger level", with no way to know:

- **which triggered first**, if both stop-loss and take-profit levels sit
  within the same day's High-Low range (a real, common case) — the current
  code picks whichever branch it happens to check first, not necessarily
  what actually happened intraday
- **the actual fill time**, which is stamped as the bar's own timestamp
  (start of day, or whatever the bar index represents) regardless of when
  during the day the level was actually crossed — this feeds directly into
  financing/overnight-cost timing and any time-based reporting
- **whether a margin-call/stop-out condition that both breached and
  recovered within the same coarse bar was ever actually hit** — `check()`
  only sees the bar's aggregate state at evaluation time, not any intrabar
  path

A caller that separately has access to finer-grained data for the same
symbol/period (Kairos, for one, maintains its own intraday mirror
specifically to get a fresher/finer price than what it feeds into
`runner.backtest()`'s own bars) currently has no way to make phantom use it
for this purpose — `determine_close()`/`MarginEngine` have no hook to accept
or request finer bars than the ones the step loop is already iterating on.

## File Locations

- `src/phantom/engine/position_manager.py` — `determine_close()` (~line
  242-300+)
- `src/phantom/engine/margin_engine.py` — `MarginEngine.check()` (~line
  17-56), `handle_stop_out()` (~line 100-172)
- `src/phantom/engine/simulation_engine.py` — the step loop that fetches
  `bars_today` once per ticker per step and passes that single bar
  everywhere (`_fetch_all_ticker_bars()`, `_evaluate_pending_orders()`, the
  `open_positions` TP/SL loop, the margin-check call site)
- `src/phantom/data/provider.py` (`DataProvider` interface) — would need a
  way to express "give me the finest interval you have for this
  ticker/range", or an explicit secondary provider parameter

## Current State

No intrabar refinement exists anywhere in the engine today. Every
close/liquidation decision is made from exactly one bar at exactly the
resolution the caller's `data_provider` happened to return for the step's
`start`/`end`.

## Acceptance Criteria

- [ ] `SimulationEngine`'s constructor or `run_backtest()`/`run_paper()`
      accepts an optional finer-resolution `data_provider` (or the primary
      `DataProvider` gains a way to signal it can serve multiple
      resolutions) used specifically for TP/SL/margin-call/stop-out
      resolution within a coarser step
- [ ] When a finer provider is available and a step's bar brackets BOTH a
      stop-loss and take-profit level (or crosses a margin threshold),
      `determine_close()`/`MarginEngine.check()` walks the finer bars in
      time order to find which was actually hit first, and stamps the real
      trigger time rather than the coarse bar's own timestamp
- [ ] When no finer provider is supplied, behavior is unchanged (single-bar
      High/Low check, current tie-breaking) — this is additive, not a
      required input
- [ ] New test: a daily bar whose High/Low brackets both TP and SL, with a
      supplied hourly provider showing the SL level was actually crossed
      first — `determine_close()` returns the SL outcome, not TP
- [ ] New test: same setup with no finer provider supplied — existing
      (documented, unchanged) tie-break behavior is preserved

## Implementation Notes

This is the largest of the four E17 tickets — probably worth scoping
narrower for a first pass (e.g., just `determine_close()`'s TP/SL
resolution, leaving margin-call/stop-out intrabar precision for a follow-up)
rather than doing all of it at once. Even TP/SL-only would remove the
biggest source of ambiguity for a caller running multi-day backtests at
daily resolution.
