# E17-S07: No Update API for a Loaded Broker Profile

**Epic:** E17 — CFD Margin & Order-Fill Correctness
**Phase:** Enhancement (found during downstream validation, not part of a feature sequence)

## Description

`BrokerAPI`/`BrokerRepo` support `create`/`get`/`get_by_name`/`list`/`delete`/
`load`/`validate` — there is no `update`. A caller that needs to change an
already-loaded broker profile's config (e.g. its margin `classes`, per
E17-S01) has no supported way to do so: `delete` + re-`create`/`load` mints a
new profile `id`, orphaning `account.broker_profile_id` foreign keys on any
account already created against the old profile in the same persistent
`data_dir`.

This was caught because a downstream project (Kairos) needed exactly this —
after E17-S01 shipped per-instrument-class margin rates, Kairos found
phantom's bundled `ibkr.json` classes use IBKR-native symbol spellings that
never match its own (yfinance-style) tickers, and needed to patch the loaded
profile with its own margin classes to make E17-S01 actually apply (see
E17-S08, filed alongside this ticket, for the matching-conventions side of
that problem). With no update API, Kairos's `_sync_margin_classes()`
(`kairos_papertrade.py`) reaches directly into `client._conn` and does a raw
`UPDATE broker_profiles SET config_json = ? WHERE id = ?` to preserve the row
id — working, but exactly the kind of private-schema reach-through the public
API should make unnecessary.

## File Locations

- `src/phantom/api/brokers.py` — `BrokerAPI` (add `update`)
- `src/phantom/db/repositories/broker_repo.py` — `BrokerRepo` (add `update`,
  alongside existing `create`/`get`/`get_by_name`/`list`/`delete`)

## Current State

```python
# broker_repo.py
def create(self, profile: BrokerProfile) -> BrokerProfile: ...
def get_id_by_name(self, name: str) -> str: ...
def get(self, profile_id: str) -> BrokerProfile: ...
def get_by_name(self, name: str) -> BrokerProfile: ...
def list(self) -> list[BrokerProfile]: ...
def delete(self, name: str) -> None: ...
```

No `update`. `BrokerAPI` mirrors the same gap (`load`/`create_from_dict`/
`list`/`get`/`validate`, no `update`).

## Acceptance Criteria

- [ ] `BrokerRepo.update(profile: BrokerProfile) -> BrokerProfile` writes the
      existing row (matched by `id`, from `profile.name` or an explicit id
      param — whichever fits the existing `create`/`get_by_name` convention
      better) in place, preserving its `id`
- [ ] `BrokerAPI.update(name: str, profile: BrokerProfile) -> BrokerProfile`
      (or equivalent) exposed on the public API, same signature style as
      `create_from_dict`
- [ ] Raises `NotFoundError` (matching `get`/`get_by_name`'s existing
      behavior) if no profile with that name exists yet — `update` is not an
      upsert
- [ ] Accounts already created against the profile's `broker_profile_id` are
      unaffected — same `id`, only `config_json` changes
- [ ] New test: create a profile, place/fill an order against an account
      using it, call `update` with a modified margin config, confirm the
      account's `broker_profile_id` still resolves and the NEW margin config
      applies to the next order

## Implementation Notes

Kairos's `_sync_margin_classes()` is a working reference for the exact
before/after comparison + idempotent-no-op pattern a caller wants around this
(don't write if nothing changed) — that part can stay caller-side, this
ticket is just about giving callers a real API instead of a raw SQL
UPDATE on private schema.
