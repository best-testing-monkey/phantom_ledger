# E17-S03: Margin-Call/Stop-Out Liquidation Ignores Per-Position Margin

**Epic:** E17 — CFD Margin & Order-Fill Correctness
**Phase:** Bug (found during downstream validation, not part of a feature sequence)

## Description

Since `ee31835`, each CFD `Position` correctly stores its OWN
`margin_required`/`leverage` at fill time (see E17-S01 for the remaining gap
in what rate that uses). But `MarginEngine.check()` and
`MarginEngine.handle_stop_out()` never read that field — they independently
recompute a portfolio-wide `used_margin` from scratch:

```python
# check()
open_position_market_value = sum(p.notional for p in open_positions)   # ALL positions, any instrument_type
used_margin = open_position_market_value * broker_profile.margin.default_margin_pct
```

Two separate problems here, both stemming from not trusting the per-position
`margin_required` that fill-time already computed correctly:

1. **Wrong instrument types are included.** `open_positions` is filtered
   only by "does this account have at least one CFD position" (`has_cfd`
   gate, one level up) — but `open_position_market_value` itself sums
   `p.notional` across *every* open position passed in, including plain
   `"stock"` positions that had their full notional debited as cash at
   entry and carry zero real margin exposure. A CFD account that also holds
   stock positions will have its margin usage overstated by however much
   stock notional it's carrying.
2. **Uses today's flat rate, not the rate actually locked in at entry.**
   Once E17-S01 lands (per-instrument-class rates, rate can vary by ticker,
   and in principle a profile's rates could even change over time), this
   recompute will silently diverge from the sum of each position's own
   stored `margin_required` — which is the number that actually reflects
   what cash/margin was really set aside for each position.

The same `handle_stop_out()` cascade repeats the identical
`remaining_market_value * broker_profile.margin.default_margin_pct` pattern
per iteration, so it inherits both problems too. It also sorts the
close-first order by `p.unrealized_pnl` — this needs its own check, since
`docs/library.md` documents `Position.unrealized_pnl` as "a permanent 0.0
stub" (never actually computed/persisted anywhere per that audit). If that's
still accurate, `sorted(open_positions, key=lambda p: p.unrealized_pnl or
0.0)` sorts everything as equal (stable sort → insertion order), so the
"largest loss first" doc comment on `handle_stop_out()` does not currently
hold — closes happen in whatever order `open_positions` was passed in, not
by loss size. Worth confirming/fixing as part of this same ticket since it's
the same code path.

## Current State

See code excerpts above. `position.margin_required` exists and is populated
correctly at fill time (post E17-S01/`ee31835`) but nothing in
`margin_engine.py` reads it.

## Acceptance Criteria

- [ ] `MarginEngine.check()`'s `used_margin` is the sum of open CFD
      positions' own `margin_required` field, not a portfolio-wide notional
      recompute
- [ ] Non-CFD (`instrument_type != "cfd"`) positions never contribute to
      `used_margin`
- [ ] `handle_stop_out()`'s per-iteration margin recompute uses the same
      per-position `margin_required` sum (minus whatever's already been
      closed in the cascade), not `remaining_market_value * default_margin_pct`
- [ ] `handle_stop_out()`'s close order actually reflects largest-loss-first,
      using a real unrealized-P&L figure (computed from current
      price/entry_price/quantity/direction, matching e.g. how a downstream
      caller like Kairos's `kairos_mtm.unrealized_pnl()` does it) if
      `Position.unrealized_pnl` is confirmed still a stub — or reads the
      real field if it's since been implemented elsewhere
- [ ] New test: an account with one stock position and one CFD position at
      `stop_out` level only counts the CFD position's margin; the stock
      position is never liquidated by this path
- [ ] New test: `handle_stop_out()` closes the position with the largest
      unrealized loss first when given positions with distinct P&L

## Implementation Notes

This should share whatever per-instrument-class rate lookup E17-S01
introduces, and ideally the same small helper E17-S02 suggests extracting
for margin-rate lookups — three independent copies of "what's the margin
rate for this position" is exactly how this and E17-S01 diverged from
`handle_fill()` in the first place.
