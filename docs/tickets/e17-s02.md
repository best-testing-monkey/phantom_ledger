# E17-S02: A Single Order's Fill Failure Aborts the Whole Batch

**Epic:** E17 — CFD Margin & Order-Fill Correctness
**Phase:** Bug (found during downstream validation, not part of a feature sequence)

## Description

Inside `SimulationEngine`'s per-step loop, every newly-triggered order fill
is processed in a plain `for` loop with no per-order error handling:

```python
new_fills = self._evaluate_pending_orders(active, bars_today)
for filled_order in new_fills:
    filled_order_obj, position = self._order_manager.handle_fill(
        filled_order, self._position_repo
    )
    ...
```

`OrderManager.handle_fill()` can raise `InsufficientFundsError` (line ~312,
`if account.cash < total_deduction: raise ...`) whenever a single order's
required cash/margin exceeds the account's current balance — a completely
normal, expected outcome for an account trading near its limits, not an
exceptional condition. Because it isn't caught here, it propagates out of
the whole time-step's loop, out of `run_backtest()`'s `while not
clock.is_done()` loop, and out of `run_backtest()`/`run_paper()` entirely.

The practical effect: if `new_fills` contains, say, 5 orders for 5 different
tickers and the 3rd one can't be funded, the account never processes fills 4
and 5, never evaluates open-position TP/SL/liquidation for that step, and
(depending on the caller) the *entire remaining date range being backtested*
can be abandoned — a caller that wraps `run_backtest()` in a broad
`try/except` (a very natural thing to do around a library call) sees "the
call failed", not "one order among several couldn't be funded", and has no
way to tell which order was the problem or that the other 4 would have
succeeded fine.

This directly compounds E17-S01: once a caller starts sizing positions to a
real per-instrument leverage figure, hitting the account's margin ceiling on
*any single instrument* becomes a routine, expected event during normal
operation — not something that should ever take down an entire step's
processing for every other ticker.

## File Locations

- `src/phantom/engine/simulation_engine.py`:
  - `run_backtest()`, fill loop ~line 197-204
  - `run_paper()`, fill loop ~line 547 (same pattern)
  - a third fill loop ~line 709 (same pattern)
- `src/phantom/engine/order_manager.py` — `handle_fill()` (~line 311-316,
  the raise site); `place()` already has a `place_or_reject()` sibling
  (~line 61) that catches `InsufficientFundsError`/`MarginError` and returns
  a `status="rejected"` order instead of raising — `handle_fill()` has no
  equivalent

## Current State

None of the three fill loops in `simulation_engine.py` catch anything around
`handle_fill()`. `OrderManager` already has the *pattern* to copy
(`place_or_reject`), it's just never been applied to the fill path.

## Acceptance Criteria

- [ ] A single order's `InsufficientFundsError` (or `MarginError`, if that
      can also raise at fill time) during a fill pass results in that ONE
      order being marked `status="rejected"` / `rejection_reason` set, and
      processing continues for the rest of that step's other orders and for
      subsequent open-position handling
- [ ] `run_backtest()` and `run_paper()` both still process every OTHER
      fillable order in the same step when one fails
- [ ] `BacktestResult` (or an equivalent field on the paper-trading return
      value) surfaces which orders were rejected at fill time, not just
      silently drops them — a caller needs to be able to count/observe this,
      the same way `place_or_reject()`'s rejected orders remain queryable
      via `orders.list(status="rejected")`
- [ ] Existing tests around `handle_fill()` raising `InsufficientFundsError`
      still pass (single-order behavior unchanged) — only the multi-order
      containing behavior changes
- [ ] New test: a batch of fills where the 2nd of 3 orders can't be funded
      results in orders 1 and 3 filled, order 2 rejected, no exception
      propagates out of `run_backtest()`

## Implementation Notes

Straightforward `try/except InsufficientFundsError` (and `MarginError` if
applicable) around each `handle_fill()` call site, converting to the same
rejected-order bookkeeping `place_or_reject()` already does. Three call
sites to update, ideally by extracting a small shared helper so they can't
drift apart the way `MarginEngine`'s margin-rate lookups already have (see
E17-S01).
