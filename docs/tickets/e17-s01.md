# E17-S01: Per-Instrument-Class CFD Margin Rates

**Epic:** E17 — CFD Margin & Order-Fill Correctness
**Phase:** Bug (found during downstream validation, not part of a feature sequence)

## Description

`ee31835` ("Fix CFD orders not applying leverage/margin accounting") made CFD
fills correctly deduct margin instead of full notional — a real fix. But the
margin rate it uses, `broker_profile.margin.default_margin_pct`, is a single
flat percentage for the *entire broker profile*, applied to every CFD
instrument regardless of asset class. Real brokers (including IBKR, whose
bundled profile ships `default_margin_pct: 0.25`) charge very different
initial margin by asset class — FX majors are commonly ~3%, index/gold
futures ~5%, other commodities ~10%, single-name equity CFDs ~20%, and some
crypto CFDs are effectively unleveraged (100%). A flat 25% for all of them is
wrong in both directions: it's far too strict for FX/futures (a caller sizing
a position for realistic 20-30x FX leverage will find phantom only grants 4x
and refuses the rest of the fill) and can be too loose for instruments that
should carry little or no leverage at all.

This was caught because a downstream project (Kairos) already models
per-asset-class margin independently (see its `config/margin_ibkr.yaml`) for
its own sizing/risk decisions, and that per-class rate diverges sharply from
phantom's flat rate — a downstream caller's admission logic can believe an
order is safely within margin (using its own, more accurate rate) while
phantom's `handle_fill()` disagrees and raises `InsufficientFundsError`
because it's using the flat 25% instead. See E17-S02 for the compounding
effect of that mismatch.

## File Locations

- `src/phantom/engine/order_manager.py` — `handle_fill()` (~line 298-316),
  `margin_pct = broker_profile.margin.default_margin_pct`
- `src/phantom/engine/margin_engine.py` — `MarginEngine.check()` (~line 33)
  and `MarginEngine.handle_stop_out()` (~line 148), both independently read
  `broker_profile.margin.default_margin_pct` again
- `src/phantom/models/broker.py` (or wherever `BrokerProfile`/margin config
  is modeled) — schema currently has one `default_margin_pct` field
- `src/phantom/profiles/ibkr.json` (and `degiro.json`, `xtb.json`) — bundled
  profiles that would need a per-class table

Same flat lookup independently duplicated in `MarginEngine.check()`:


and in `MarginEngine.handle_stop_out()`'s per-iteration recompute. All three

funnel through one shared helper so they can't drift from each other again.

## Acceptance Criteria

- [ ] `BrokerProfile.margin` supports a per-asset-class (or per-symbol
      override, or regex-match) margin table, with `default_margin_pct`
      retained as the fallback for anything unmatched
- [ ] `handle_fill()` looks up the rate for the specific ticker/instrument
      being filled, not a single account-wide constant
- [ ] `MarginEngine.check()` and `handle_stop_out()` use the SAME per-symbol
      lookup (ideally the same helper function) rather than re-reading
      `default_margin_pct` directly — see E17-S03, which also needs this
- [ ] Bundled `ibkr.json`/`degiro.json`/`xtb.json` profiles ship reasonable
      per-class defaults (FX majors, indices/commodities, equity CFDs,
      crypto) instead of one number
- [ ] Existing single-rate behavior is preserved when a profile's margin
      table has no class entries (backward compatible for callers/tests that
      only set `default_margin_pct`)
- [ ] Unit test: two CFD fills on the same account with tickers mapped to
      different classes end up with different `position.margin_required` /
      `position.leverage`

## Implementation Notes

Consider mirroring the shape Kairos already uses for its own (independent)
margin config — a list of classes, each with a `match` (regex on ticker) or
explicit `symbols` list, first match wins, `default_margin_pct` as the
catch-all. Doesn't need to be identical, just needs *a* per-class mechanism;
right now there is none.
